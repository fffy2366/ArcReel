# 剧游策划工作流

你负责把一个 PlayAsLife 项目上游扩展为“剧游内容生产项目”。剧游频道的数据保存在：

`projects/{project_name}/story_game/index.json`

不要把长篇正文写入 `project.json`。`project.json` 只保留 PlayAsLife 原有的视频生产元数据。

## 核心流程

1. 项目设定：标题、题材、市场、语言、游戏类型、计划章节数。
2. 生成故事梗概，必须人工确认或人工修改后才能进入下一步。
3. 基于已确认梗概生成世界观，必须人工确认或人工修改后才能进入下一步。
4. 基于已确认梗概和世界观生成角色设定。
5. 创建 Brief，并保存用户画像、必须包含、必须避免。
6. 根据 Brief 一次生成 5 篇广告剧本，每篇必须有不同叙事骨架和不同玩法落点。
7. 选择验证通过的广告作为正文源。
8. 分批生成章节目录，每批 20 章，直到 planned_chapters。
9. 单章生成连续详纲。
10. 单章生成正文草稿。
11. 优化成 1900-2300 字正式正文。
12. 导出为 PlayAsLife `scripts/episode_N.json`，再进入分镜/视频生产流水线。

## 调参位置

Web 频道按钮调用 FastAPI 服务，不会自动把本文件读进模型上下文。线上 Web 生成的核心提示词和玩法库在：

`server/services/story_game_registry.py`

重点函数：

- `GAMEPLAY_LIBRARY`
- `story_synopsis_prompt`
- `story_world_prompt`
- `story_characters_prompt`
- `ad_prompt`
- `ad_gameplay_integrate_prompt`
- `detail_prompt`
- `chapter_draft_prompt`
- `chapter_polish_prompt`

`server/services/story_game.py` 负责状态保存、API 编排和调用 `TextGenerator`，不要在里面重复维护玩法库或长提示词。

本 Skill 用于 Claude Agent SDK runtime 和 subagent 行为约束。修改本文件后，也要同步修改 `server/services/story_game_registry.py` 中对应提示词，避免 Web 频道和 Agent runtime 行为不一致。

## 对话式文章编辑

当用户在左侧 Agent 中要求“修改故事梗概/世界观/角色设定”“修改广告”“重写某条广告”“调整详纲”“改正文”时，优先使用 PlayAsLife MCP 工具，不要直接编辑 `projects/{project_name}/story_game/index.json`。

可用工具：

- `mcp__playaslife__get_story_game_state`：先查看当前项目设定、Brief、广告列表、选中广告、章节状态，用于定位 id 和状态。
- `mcp__playaslife__patch_story_game_settings`：保存剧游设定字段，支持 `title`、`market`、`target_language`、`genre`、`planned_chapters`、`gameplay_type`、`synopsis`、`world_setting`、`characters_text`、`audience`、`story_direction`、`must_include`、`must_avoid`。
- `mcp__playaslife__rewrite_story_game_ad`：按用户自然语言要求重写指定广告并保存。默认 `keep_gameplay=true`，除非用户明确要求更换玩法。
- `mcp__playaslife__patch_story_game_text`：保存用户确认后的文本。`target_type` 支持 `ad`、`chapter_detail`、`chapter_draft`、`chapter_final`。

操作规矩：

1. 先调用 `get_story_game_state`，不要凭记忆猜广告 id 或章节号。
2. 用户说“修改故事梗概/世界观/角色设定/用户画像/剧情方向/必须包含/必须避免”时，调用 `patch_story_game_settings`，不要调用 `patch_project`。
3. 用户说“把第 4 条广告改成更暧昧但保持跑酷玩法”时，定位对应广告后调用 `rewrite_story_game_ad`。
4. 用户直接给出一段替换文本时，使用 `patch_story_game_text` 保存到对应广告、详纲、草稿或正式正文。
5. 修改详纲前确认该章节已有详纲；没有详纲时先让用户去生成详纲或调用对应 Web 流程。
6. 一次只改用户指定的设定、广告或章节，不要顺手批量覆盖其它内容。
7. 修改后简短说明已更新的目标、玩法是否保持、是否需要用户刷新页面查看。

## 玩法原则

广告和正文必须先从项目的游戏类型读取玩法菜单，再融合剧情。

### 修仙玩法

可用主玩法包括：追杀跑酷、炼丹开炉、画符镇压、布阵破禁、斗法护人、鉴宝识伪、炼器锻造、破境稳脉、天劫生存、小世界经营、灵宠驯服、宗门防守、御剑空战、净化封印。

黑市、交易会、拍卖只能作为剧情场景，不作为主玩法。

### 恋爱收集养成玩法

定位：男性向第一人称男友视角恋爱收集养成 + 点击赚钱。

核心循环：玩家就是男主 → 点击招财猫赚钱 → 投入女主危机/关系/成长 → 好感度/亲密度/关系阶段变化 → 解锁视频片段/动态立绘/语音/图鉴/新女主。

可用主玩法包括：招财猫点击赚钱、解围消费、送礼好感、约会安排、男主健身魅力、应援打榜、换装立绘、关系任务、事业投资、视频卡片解锁、美女图鉴收集。

禁止把女主写成被购买的奖品。花钱必须服务解围、关心、成长、约会、事业或共同目标。

### 系统文玩法

可用主玩法包括：系统任务选择、属性加点、限时任务、奖励抽取、技能树解锁、身份伪装、经营收益、反派值/声望值管理。

系统必须带来目标、倒计时、奖励、惩罚和成长反馈。

### 反弹球玩法

可用主玩法包括：弹球破盾、轨道反弹、连击清屏、Boss 弱点打击、道具球组合、护盾反弹、救援倒计时、障碍解锁。

反弹球必须和剧情目标绑定，例如破盾、开门、救人、反击或清除障碍。球是玩家发射的子弹，用来打龙、打龙身关节、打 Boss 弱点和阻止龙手压线，不是抽象小游戏。

弹球打龙基础战场：Boss/龙首在屏幕正上方并显示血条，两只龙手或龙身关节从上方向下压迫；玩家在屏幕下方发射球形子弹，靠角度、反弹、穿透、爆炸、范围伤害、控制和召唤效果击打龙身。失败压力来自龙手到达底线、Boss 血条未清空、救援倒计时耗尽或关键通路未打开。

当主玩法是“道具球组合”时，必须先参考 `references/rebound-ball-item-bullets.md`，从球种表里选择 2-4 种球形子弹组合进剧情；不要把整个球库全塞进一场戏。道具球不是剧情道具、装备奖励或抽卡藏品。

### 外卖玩法

定位：修真界送丹外卖订单驱动玩法，用于《修真外卖员：丹药送到，师姐别乱来》这类项目。

可用主玩法仅限：炼丹、辅助修炼、御剑飞行。

男主固定为筑基初期内门弟子，自己经营一家小型外卖丹铺，会基础炼丹和御剑飞行。不要再写成毫无修为的废柴杂役，也不要写成第一章才突然获得御剑或炼丹能力。

核心循环统一称为“订单修炼循环”：

接单 → 凑材料 → 挂机炼丹 → 成丹 → 御剑送丹 → 路上自动飞行/清怪/收集材料 → 抵达目的地 → 女修服丹 → 手动辅助修炼 → 获得灵石、特殊材料、法宝或丹炉升级件 → 解锁更高级订单。

接单、送丹、订单超时、洞府签收是叙事包装，不是第四种主玩法。广告、详纲、正文只能从三类核心交互中选一种作为本章/本条广告的唯一主玩法。

- 炼丹：挂机炼丹/抽奖保底系统，发生在男主自己的外卖丹铺、丹房或出发前订单准备阶段，绝不能写成到了收货人面前才现场开炉。玩家选择订单、检查材料、投入丹炉后自动炼丹；丹炉持续吐出废丹、低品丹、半成丹，挂满时间后 100% 产出目标丹药。UI 使用订单面板、材料槽、炼丹队列、挂机倒计时、废丹/低品丹跳出、保底进度、成丹品质。
- 辅助修炼：女修服丹后药力失控，玩家调整姿势或经脉节点，让药力光点对准正确经脉光圈，稳住呼吸节奏，清除堵塞、丹毒、心火或魔气。UI 使用经脉图、药力光点、经脉光圈、呼吸节奏圈、真气流速、反噬风险、突破进度。动作可以荒唐搞笑、有误会和暧昧，但本质必须是救命、修炼、稳境、突破。
- 御剑飞行：半挂机送丹和材料收集，不是复杂手操跑酷。男主装载丹药后自动御剑出发，自动飞行、自动清怪、自动收集灵气/药草/妖兽材料；数值达标才击杀路途 Boss 或突破阻碍。UI 使用配送倒计时、丹药保护状态、自动飞行路线、清怪进度、材料收集提示、护送数值、追兵距离。

正文以剧情推进为主，玩法不是每章都必须完整出现；只有当剧情自然走到订单、炼丹、送丹或服丹异常时，才进入对应玩法。没有自然触发点时，按纯剧情写，不要硬塞 HUD、按钮、结算或玩法 UI。

禁止混入画符、布阵、鉴宝、炼器、塔防、经营、抽卡、选择题、弹球打龙、拍照评分等其它项目玩法。变化可以来自订单等级、女修状态、场景、追兵、丹药品阶、丹炉等级、材料稀缺和失败压力，但核心只能是这三类。

## 广告剧本硬约束

- 创建/生成广告前，Brief 必须先由用户人工确认“语言的钉子”：一句所有广告共同强化的记忆句、口号、反复出现的台词或情绪判断。没有语言钉子，不要开始生成广告。
- 每篇广告必须在 `full_script` 中原句写入 Brief 的语言钉子，不能改写成近义句。
- 每篇广告必须输出 `visual_hammer`：AI 根据该篇剧情自动提炼的一句标志性画面。视觉锤必须可拍、可生图/生视频、可被用户记住，并服务同一个语言钉子。
- 视觉锤不是抽象主题，不是“压迫感很强”“宿命感很强”，而是画面，例如“暴雨里女主一手按住主角伤口，一手把发光炉鼎纹推回他胸口，手机游戏 UI 的体力条贴着红线闪烁”。
- 每篇广告必须在 `full_script` 中自然出现一句 TikTok 互动话题句，优先放在最后 5 秒或剧情反转后。话题句要引发站队、选择、道德判断或玩法策略讨论，例如“如果是你，这笔钱会替她花吗？”“你觉得他该先救她，还是先保住自己的底牌？”禁止生硬写“评论区扣1”“快来评论”或与剧情无关的泛问题。
- 3 秒内强危机。
- 至少一个女性角色高张力介入桥段。
- 如果女主/女异能者/源火异能者被龙族束缚、囚禁、寄生、抽取、献祭、封印、锁在龙巢或作为城市锚点，她就不能自由工作、坐诊、巡诊、开店或主动救治大量路人。
- 治疗系角色被龙束缚时，正确写法是治疗力被龙巢抽取、被迫供能、虚弱求救，或在挣扎中短暂救男主；不要写成正常医生还在医院治病救人。
- 必须服从 Brief 或项目设定中的剧情方向。用户要求情感、爱情、暧昧拉扯、守护救赎时，危机要来自误会、保护、身份暴露、关系选择、共同困境或情绪爆发，不要默认写成追杀、杀戮、灭门、连环打斗。
- 45-60 秒左右。
- full_script 是一整篇连续剧情，不是分条提案。
- 关键帧另写在 keyframes。
- 每篇广告只能融合一个可操作主玩法。
- 用户选择某个具体玩法后，该广告的游戏段只能写这一种玩法；其它玩法名不能作为按钮、模式、材料、UI 或操作流程出现。例如选择“追杀跑酷”时，只能写奔逃、跳跃、滑铲、闪避、路线判断、体力/速度/障碍/追兵距离，不能再写画符、炼丹、布阵等。
- 玩法必须从剧情困境里长出来。
- 玩法段必须出现游戏 UI 入画：HUD、资源条、风险条、按钮、技能栏/礼物栏/图鉴/血条等。
- 禁止只有选择题、只拖线、只点亮符号、只点确认。
- 禁止未成年人相关暧昧、露骨性内容、性暴力细节、照搬现有 IP。
- 当前 Web 广告生成主链处于非阻断审核模式：提示词仍要求单一玩法、语言钉子、视觉锤、角色锁和 TikTok 互动话题句，但生成结果暂不因本地质检或 Critic 未通过而卡死。重新开启阻断审核时，返工最多 3 次；第 3 次仍不合格时，必须认定该条生成失败并返回失败原因，不要继续循环重写。
- 广告生成失败不是丢弃信息：系统会把失败原因写入 `ad_failure_learnings`，归类为玩法混入、伪玩法、缺少语言钉子、缺少视觉锤、结构化输出错误、生成超时或通用质检失败。
- 下一次重试、下一条广告和下一轮生成必须读取最近失败学习记录，并逐条执行其中的修正建议。不要重复台账里的同类错误。
- 失败学习只用于修正创作行为，不要把“失败原因”“质检记录”“学习台账”写进广告正文。

## 角色设定硬约束

每个核心角色必须包含：

- 名字
- 身份
- 外表形象
- 穿着
- 核心追求
- 人物关系
- 戏剧功能
- 成长线

角色设定要服务生图、生视频和长篇剧情推进。人物关系要写欲望冲突和互相需要，不能只写标签。

## 正文硬约束

- 先目录，再详纲，再正文草稿，再正式正文。
- 一次只写一个章节。
- 每章只能有一个 `chosen_gameplay_family`，必须来自当前项目 `gameplay_type` 对应的玩法菜单。不要自己发明“选择题互动”“拖线小游戏”“点击确认”等伪玩法。
- 详纲、草稿、正式正文必须沿用同一个 `chosen_gameplay_family`。如果本章是“追杀跑酷”，整章只能写奔逃、跳跃、滑铲、闪避、路线判断、体力条、追兵距离、障碍提示等跑酷玩法；不能在同一章加入炼丹、画符、布阵、破境、天劫等其它玩法。
- 玩法融合必须写成剧情高潮里的真实可操作系统：玩家做什么、UI 显示什么、资源/风险如何变化、成功和失败反馈是什么。禁止只写“选择 A/B”“点击确认”“QTE”“拖拽连线”“小游戏开始”。
- 玩法相关词只能服务本章唯一玩法。其它玩法可以作为世界观名词轻微出现，但不能成为按钮、模式、材料槽、操作流程、系统提示或玩家任务。
- 目录不是孤立标题列表，要同时维护隐藏连续性字段：本章承接、结尾暗扣、预计回收计划、长线功能。
- 详纲必须是 900-1300 中文字连续详纲，不要只给零散条目。
- 详纲第一段必须接住上一章结尾钩子或前文未解决危机，不能跳到无关新剧情。
- 详纲必须记录本章回收了哪些暗扣、新埋了哪些暗扣、这些暗扣后续准备如何回收。
- 重大暗扣必须进入剧情记忆账本，而不只是写在上下文里。重大暗扣包括重要角色假死/失踪、身份秘密、神器代价、旧案真相、救命债、仇怨和承诺。
- 剧情记忆账本包括：长期暗扣、角色动态状态、关系债务。跨几十章回收的内容必须依赖账本，不依赖模型记忆。
- 角色公开状态和真实状态不一致时必须写入角色动态状态，例如“众人以为陆沉已死 / 实际被卷入古修洞府修炼”。
- 人情、亏欠、救命债、仇怨、承诺必须写入关系债务，后续章节要能作为情绪爆点回收。
- 正文开头必须从上一章结尾、未解决危机或人物动作直接接上；不能“换场换事”导致断集。
- 每 3-5 章至少回收一个前文暗扣，不能只挖坑不填坑。
- 正文像剧本化小说：画面环境、细节、心理活动、微表情、动作、对话、旁白、剧情推进都要在正文中自然体现。
- 玩法融合在剧情里，不要单独贴玩法说明；一章只验证一种玩法，不要为了显得丰富而混入第二种玩法。
- 章节结尾必须是追更卡点，不是说明总结。优先卡在：新人物突然出现、敌人追到眼前、主角动作被迫中断、身份/秘密即将暴露、关键物品异动、女主/反派当场发难、生死选择倒计时。
- 最后 150-300 字必须进入“下一秒就要出事”的现场；卡点句之后立即结束本章，不要再解释、总结、转场或补设定。
- 只能出现一次“本章完”，且必须放在全文最后；禁止输出完成结算、人物状态、获得物品、未解线索、操作清单等生产备注。
- 正式正文目标 1900-2300 中文字。
